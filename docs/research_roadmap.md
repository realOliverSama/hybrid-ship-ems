## 1. 研究的起点：从一个真实工程项目到研究问题

### 1.1 我手头有什么（研究的全部初始输入）

本研究的物质基础来自作者参与的**示范船 EMS 硬件在环（HIL）平台工程项目**
（工作汇报自 2026-01 起按月留档）。研究立项时，手头只有三样东西：

1. **电气系统架构图**：甲醇混合动力船单线图 + 直流配电板系统图——
   甲醇发电机组（潍柴 WH17ME，500 kW/单机 ×2）经整流挂直流母排，
   动力电池（1071.36 kWh，576 V × 930 Ah/侧 ×2）经双向 DC/DC 挂同一母排，
   推进逆变器驱动推进电机——**直流母排下机组转速与推进负荷解耦**；
2. **船舶用途**：近海工作/示范船，工况包含离泊、港区限速、经济巡航、
   赶班、桥区限速、逆水、靠泊等完整航次序列；
3. **主要部件选型**：机组、电池、推进电机的额定参数与厂家资料
   （潍柴 WH17ME 页面存档、设备参数表 2026-05-26 版，后入库
   `docs/reference/20260526设备参数.md` 作为模型标定的原始依据）。

此外有 EMS 接口表（V1.0，2026-04-20）界定了 EMS 与平台其余部分的信息边界。
**除此之外没有任何现成的模型、数据或结论**——后续的一切都从这三样东西推导。

### 1.2 从架构图读出核心物理问题

把架构图和选型参数放在一起，会出现一个关键观察：甲醇机的燃油消耗率
（BSFC）随负荷强烈非线性——低负荷时恶化显著（最优 427 g/kWh，25% 负荷时
恶化 +30%~+70%，双真实锚点标定）。电池作为能量缓冲，可以在低负荷时放电
（让机组少发或不发）、高负荷时充电（让机组高效运行），从而**把机组运行点
搬移到高效区**。

**研究目标**由此确定：设计一种能量管理策略（EMS），在保证电量维持
（电池不放干）的前提下，最小化全程甲醇消耗。

**为什么值得研究**：这个方向不是凭空设想的——它的动机来自两次失败的
研究尝试（§2），以及上述物理观察：BSFC 非线性意味着"运行点优化"空间
真实存在。但**空间存在 ≠ 实时算法能捕获**——这正是本研究要回答的问题。

### 1.3 建模的第一步：从参数表到可复现的仿真模型

有了参数，第一步不是设计控制器，而是**把船建成可复现的模型**：

| 时间 | 里程碑 | 回答的问题 |
|---|---|---|
| 2026-05-26 | 设备参数表定稿（图纸值 + ASSUMED 标注分离） | 哪些参数真实、哪些需要假设 |
| 2026-06-16 | `ship_parameters0616.m` 统一参数脚本 | 参数单一来源，杜绝散落 |
| 2026-07-30 | `HybridShip0730.slx` 首个整机模型 | 功率流能否闭合 |
| Model A MVP | 最小闭环验证模型（脚本驱动 01~07 重建，禁止 GUI 手工状态）：静止起步→巡航→固定航程，S01~S09 工况，参数按船型标定并文献交叉校核 | 规则 EMS vs 预测增强 EMS 的最小可比平台；模型可信吗 |
| Model B | 加回直流母线电气层（母线电容 + 双向 DC/DC + 整流/逆变，平均值模型） | 电压稳定与动力储备等**内部安全**维度可观测 |
| Model D | Model B 本体延续（`HybridShip_ModelD_DCBus.slx`），成为 Phase 1/2/2.5 的正式平台 | 上述全部问题在统一模型上回答 |

**建模纪律**（贯穿至今）：全部模型脚本驱动、可从零重建；图纸确定值与
ASSUMED 估计值严格分离；每个假设（BSFC 低负荷形状、DC/DC 动态参数等）
都标注来源等级，不把假设当事实用。

## 2. 研究问题的演化：两轮 NO-GO 的教训

在 Model A/B 平台就绪后，研究问题经历了三次立项。前两次尝试（2026-08-19/20，
spec `timed-feedforward-ems` 与 `multistep-predictive-ems`）均因"收益上限在
机理层面不存在"而 NO-GO，且都是在控制器施工完成后才发现：

| 轮次 | 路线 | NO-GO 原因 | 教训 |
|---|---|---|---|
| 第一轮 | timed-feedforward（定时前馈） | 收益上限机理锁死 | 控制器做完才发现上限不存在 |
| 第二轮 | multistep-predictive（多步预测） | 功率时序优化被往返损耗锁死 | 同上 |

**由此确立本研究的第一纪律**（brainstorm D1）：

> **先用离线最优（DP）验证节油收益上限存在，再投入任何控制器施工。**

这条纪律贯穿整个研究：每个 Phase 的 gate 判定都是机器可读的（JSON），不达标就不进入下一阶段，避免"施工到底才发现方向错了"的沉没成本。

## 4. Phase 0：离线收益上限验证

### 4.1 要回答的问题

> 在不考虑实时可实现性的前提下，这艘船的理论节油上限是多少？

如果上限都不到 5%，任何实时策略都不值得做（文献典型 ECMS 只能捕获上限的 60~90%）。

### 4.2 实验步骤

```text
① 设备真实参数落模（电池 1071.36 kWh、充放 1050 kW、BSFC 双锚点 427/453 g/kWh）
② BSFC 曲线族构造（双真实锚点 + 三档低负荷恶化敏感性：+30%/+50%/+70%）
③ 8 个典型场景的需求负荷剖面提取（Baseline EMS 导出，因果隔离验证）
④ 离线动态规划（DP）全局最优求解（SOC 状态网格 × P_gen 控制网格，后向归纳）
⑤ 敏感性矩阵（BSFC 档位 × 最低稳定负荷 × 爬坡率 × 电池容量）
⑥ 机器可读 GO/NO-GO 判定
```

**关键设计决策**：
- **因果隔离**：P_demand(t) 从降额与 EMS 作用之前提取，用两种控制律重复提取验证不变性（逐点偏差 <0.1%），避免"用被 EMS 影响的负荷去评估 EMS"的因果污染
- **双锚点标定**：BSFC 曲线只有两点是真实的（427 最优、453 额定），其余形状为假定——用三档敏感性量化这个不确定性
- **终端电量维持对称带**：|SOC(T)−SOC(0)| ≤ 0.005，防止 DP"借电"制造虚假节油

### 4.3 结果

| 口径 | 8 场景节油上限 | 判定 |
|---|---|---|
| 连续运行（主判定，P_min=400 kW） | 0.50% ~ 4.22% | 无场景 ≥5% |
| 同可行域（P_min=0） | 3.64% ~ 4.61% | — |
| 电池容量敏感性 | 643→0.93%，1500→6.09% | 强杠杆 |

**机器判定：DECISION_REQUIRED（tier=NONE）**——不到 5% 的 GO_ROBUST 线，也不到全低于 2% 的 NO-GO 线，落灰区。

**用户裁决：GO_TO_PHASE1**——收益机理真实存在（运行点优化，与前两轮"时序优化被锁死"机理不同），且电池容量是强杠杆（若实船电池可超配则上限可过 5%）。

### 4.4 本阶段的核心贡献

- 建立了**可复现的离线上限验证工具链**（DP 求解器 + 因果隔离 + 敏感性矩阵）
- 证明了收益机理的真实性（BSFC 非线性运行点搬移）
- 提供了 Phase 1 的标杆（DP 值将作为"上限"衡量实时算法的捕获率）

## 5. Phase 1：实时 ECMS 控制器链

### 5.1 要回答的问题

> 不依赖未来信息的实时 ECMS，能捕获 DP 上限的多少？加上"完美的未来信息"（oracle）又能再补多少？

### 5.2 控制器家族（递进设计）

| 控制器 | EMS_CTRL_LAW | 策略 | 依赖信息 |
|---|---|---|---|
| C0 | 0 | Baseline 规则（负荷跟随） | 当前负荷 |
| C1 | 4 | Fixed ECMS（λ 固定） | 当前 SOC + 负荷 |
| C2 | 5 | SOC-Adaptive ECMS（λ 随 SOC 偏差自适应） | 当前 SOC + 负荷 |
| C3 | 6 | Oracle Predictive A-ECMS（C2 + 真实未来剖面前瞻） | 当前 + **全知未来** |
| DP | — | 离线全局最优 | 全知未来 |

**ECMS 核心思想**：每步在 P_gen 可行网格上求 `argmin [ṁ_f(P_g) + λ·P_bat_eq]`——把电池的充放电折合成"等效燃油"，λ 是电价因子（kg/kWh）。

**三个研究问题**：
- **RQ1**：实时 ECMS（C2）捕获 DP 上限的比例是多少？
- **RQ2**：SOC 自适应（C2 vs C1）的增量价值是什么？
- **RQ3**：Oracle 前瞻（C3 vs C2）的增量是多少？——这是 Phase 2 NN 立项的量化依据

### 5.3 关键实验：复合航次 S20

为什么需要复合航次？Phase 0 的 8 个场景都是单一工况（静水/顺水/逆水等），15 分钟航程太短，SOC 自适应的价值体现不出来。S20 是 11 航段、92 分钟、22.5 km 的复合航次（离泊→港区限速→经济巡航→赶班→桥区限速→逆水→靠泊），低负荷段占 56.1%——足够长、足够多变，才能让 SOC 轨迹的"漂移 vs 紧致"差异显现。

### 5.4 结果（S20 复合航次，tier2 BSFC）

| 控制器 | fuel_corr [kg] | saving vs C0 | SOC_end | 捕获 DP 上限 |
|---|---|---|---|---|
| C0 Baseline | 349.00 | — | 0.5784 | — |
| C1 Fixed ECMS | 324.92 | +6.90% | **0.4394（出带）** | 72.6%* |
| C2 SOC-Adaptive | 330.66 | +5.26% | 0.6002 ✓ | **55.3%** |
| C3 Oracle Predictive | 324.96 | +6.89% | 0.6039 ✓ | **72.5%** |
| DP | 315.83 | +9.51% | 0.5963 ✓ | 100% |

*C1 出带（SOC 放到 0.44），其数字依赖大偏移下的线性修正，仅供参考。

**三个 RQ 的答案**：
- **RQ1**：C2 捕获 **55.3%**（实时、电量维持合规）
- **RQ2**：SOC 自适应的价值不是单场景节油，而是**跨航程的电量维持可迁移性**——C1 的 S01 标定 λ 在 S20 上失控（SOC 漂到 0.44），C2 全程紧致 [0.596, 0.602]
- **RQ3**：oracle 增量 **+1.63 pp**（S20 入带口径）≥ 0.5 pp 阈值

**机器判定：PROCEED_TO_PHASE2_NN**——完美未来信息有真实经济性价值（+1.63 pp），值得用 NN 去逼近。

### 5.5 本阶段的核心贡献

- 建立了完整的**实时 ECMS 控制器家族**（C1/C2/C3）+ 消融实验设计
- 证明了 SOC 自适应的必要性（跨航程电量维持）
- 量化了预测的价值（+1.63 pp），为 Phase 2 提供了立项依据
- 所有控制器为嵌入式可行设计（单步网格穷举 ≤200 点，无迭代优化器）

## 6. Phase 2：NN 预测通道

### 6.1 要回答的问题

> 用神经网络实时预测未来负荷，替代 Phase 1 中的 oracle（全知未来），能捕获多少预测增量？

- **RQ4**：NN 预测捕获 oracle 增量的比例（capture rate）
- **RQ5**：对未见过的新航次泛化如何
- **RQ6**：部署预算能否落进 STM32N6

### 6.2 预测目标设计

**关键决策**：预测**未来 300 s 能量需求 Ê_H(t) = Σ P_demand(t+1..t+300)/3600 [kWh]**，而非瞬时峰值。

为什么？前两轮 NO-GO 的教训：瞬时峰值预测是"时序优化"思路，被往返损耗锁死。能量需求预测是"运行点优化"思路，与 BSFC 非线性的节油机理对齐。

**控制器接入**：Ê_H 经 SOC_ref 前瞻通道驱动（`SOC_ref_eff = SOC_ref + K_S·ê`，K_S=0.01 保守增益）——与 Phase 1 的 C3 oracle 通道同构，构成 law=7（C4 NN-A-ECMS）。

### 6.3 数据与模型

- **fleet-200**：随机航次生成器（7 类积木）生成 200 条多样化航次，S20/S01/S02/S07 结构性隔离（不进任何 split）
- **数据集**：77,586 窗口，输入 302 维（P_demand 300 s 历史 + v_ship + accel），航次级 split **140/30/30**，归一化 fit-on-train
- **选模**：MLP 302-128-64-1（47,105 参数）击败 LSTM 对照（val RMSE 9.30 vs 10.68）
- **泄漏检查**：窗口不跨航次、split 互斥、首尾裁剪——全过

### 6.4 Simulink 集成：内联受挫 → 显式信号线接口破局

**攻坚过程**：MLP 前向内联进 MATLAB Function 块（Stateflow EML）时遭遇 `Stateflow:cdr:ErrorsParsingEmlFcn` 解析失败——系统性攻坚排除了代码语法、图对象、接线、参数值、转置形式、尺寸声明（证据链存档），根因锁定为 **R2026a EMChart 跨块变量数据流缺陷**（MathWorks 提交材料已备）。

**最终方案（内联版，已产品化）**：NN 权重不经跨块变量数据流，改经 `nnconst_*` Constant 块以**显式信号线**传入 MATLAB Function 块，绕开缺陷；过程中另发现并修正权重重排序方向问题，回退门控 `ECMS_NN_WeightsOK` 与权重注入架构对齐。原 Amendment v1.2 的 `coder.extrinsic` 兜底保留为备案方案（本轮未启用）：科学上零损失（消融语义不变），extrinsic 边界仍对应 Phase 3 的 NPU 推理 / MCU 控制分工。

**验证链**：build law 0~7 全编译；T1 函数 vs Python max|Δ|=1.2e-14（与 Windows 证据逐位一致）；T2 回退逐位 ≡ law=6(ê=0)；T3 S01 闭环 fuel=91.23 kg（与 golden 逐位一致）；内联版与兜底版 S01 结果逐位一致；Mac 端补跑全绿复现。

### 6.5 结果（S20 复合航次）

| 控制器 | fuel_corr [kg] | saving vs C0 | 备注 |
|---|---|---|---|
| C0 Baseline | 349.002 | — | Phase 1 复用 |
| C2 A-ECMS（规则） | 330.662 | 5.26% | Phase 1 复用 |
| **C4 NN-A-ECMS** | **328.549** | **5.86%** | 本阶段新跑 |
| C3 oracle-A-ECMS | 324.957 | 6.89% | 上界参照 |
| DP | 315.83 | 9.51% | 物理上界 |

**nn_oracle_capture = (330.662−328.549)/(330.662−324.957) = 0.3704 → PARTIAL**

- C4 捕获 oracle 增量的 **37%**，未达 ≥50% 合格线
- 留出泛化 **median = −0.232%**（4/10 航次为正）——收益依赖航次结构，不是普遍增益
- 部署预算**完全满足**（47k 参数、184 KB、<1 ms 推理）

### 6.6 失败模式与诚实结论

- **S07 桥区机动恶化 1.2 kg**：长时低功率段 + 突发操纵，NN 按平均能量预测导致 SOC_ref 偏移方向错误——Phase 3 需门控保护
- **低估偏向**（under_freq=0.426）：预测偏保守 → 放电偏多，在 S20 恰好有利、在 S07 有害——收益方向依赖航次结构
- **预测精度天花板**：R²≈0.73，约 27% 的未来能量方差不可由历史 300 s 解释（浪、流随机分量）——这是纯历史外推的理论上限

**机器判定：PARTIAL**。**用户裁决：带 C4 进 Phase 3**（C2 为主控制器、C4 为边缘实验对照），理由：
- C4 从未显著劣化 S20，且部署成本极小
- S07 门控保护纳入 Phase 3 设计
- 论文结论成立且诚实："预测通道的价值取决于航次可预测性"

### 6.7 本阶段的核心贡献

- 完成了**从 oracle 到 NN 的完整替代验证**（消融实验设计：C0/C2/C4/C3/DP 五级对照）
- 诚实报告了边界结果（37% capture、泛化中性）——不夸大、不隐藏失败
- 建立了**可复现的数据集/训练/集成/验证工具链**（fleet 生成器 + 泄漏检查 + 双平台交叉验证）

## 7. Phase 2.5：数据重做与预测体系换代（进行中）

> 本章是 2026-08-28 起的新主线。spec：`.specs/nn-predictive-ecms-phase25/`，
> 工作目录：`model/simulink_modelD_(EMS_NN_AECMS)/`。12 个任务（T-301~T-312）
> 组织为六个阶段，每一步都以"机器可读 gate + 用户裁决"推进。

### 7.1 Phase 2 留下了什么问题（为什么要有 2.5）

Phase 2 的结论是诚实的 PARTIAL（37% capture），复盘后发现三个深层问题：

1. **数据太"像模板"**。v1 的 200 条航次由 7 类航段积木拼成，速度档位固定——
   K-shape 聚类审计显示大量航次只是少数几个模板的时间缩放变体。神经网络在这种
   数据上拿到的 val RMSE，可能只是"背模板"的能力，不是"学物理规律"的能力。
   **换句话说：Phase 2 的预测精度可能被数据质量封了顶，而不是被模型能力封了顶。**
2. **预测只有一个点**。网络输出 Ê=100 kWh——但"有多确定"没有表达。S07 桥区
   恶化 1.2 kg 的失败模式说明：EMS 需要知道"什么时候该少信 AI"。
3. **选模只看 RMSE**。精度高 ≠ 闭环收益大 ≠ 部署成本低，三者需要共同裁决。

Phase 2.5 的目标：**把这三个问题变成可验证的工程机制**，而不只是换个网络再跑一遍。

### 7.2 顶层设计（Amendment v1.1，用户裁决）

- **三级选模协议（FR-317）**：val 指标只做"资格筛选"（淘汰明显劣势）→ 闭环
  capture（S20）+ 消融（S01/S02/S07）+ 留出门禁裁决 → NPU 成本 Pareto（int8 大小/
  时延/HW coverage）。**最终 Winner 由闭环结果决定，不是 val RMSE。**
- **所有模型输出分位数 q10/q50/q90**（pinball loss）——预测自带不确定性区间。
- **工况识别器降级为候选组件**：最后用 G0~G3 消融实验决定要不要它（若
  "分位数门控"已够好，就不额外部署一个分类网络——嵌入式系统尽量简单）。
- **S20 = benefit gate + 完全留出航次 = non-degradation gate**：修好老问题的同时
  不许把别的场景搞坏（median ≥ −0.5%、min ≥ −1.5%）。
- **T-311 必须在 N6 板上做 int8 验证**（FR-319），不是纸面估算。

### 7.3 阶段一：把数据重新做好（T-301 / T-302 / T-303）✅

**T-301：先设计"该怎么随机"（不写代码）**。逐项物理论证五个扰动机制：

| 机制 | 内容 | 裁决 |
|---|---|---|
| M0 | 数据质检硬规则：非逆水段 P_calc>700 kW 拒绝重抽；逆水段允许饱和（V_rel≤7.06 m/s 包络） | 通过 |
| M1 | 航速随机：每段型连续区间采样（eco 7~9 kn、rush 10~11.5 kn 等，告别固定档位） | 通过 |
| M2 | 水流随机：逆水 −0.6~−1.2 m/s，其余 ±0~0.3 m/s | 通过 |
| M3 | 阻力随机：k_res∈[0.95,1.15]，经模型既有 profile_code=4 通道注入（零模型手术） | 通过 |
| M4 | 避让台阶事件 | **用户裁决删除** |

**T-302：真正生成 v2 的 400 条航次**。生成（seed 20260829，平均重抽 3.12 次/航次）
→ Simulink 全量闭环仿真（400/400 零拒绝）→ 物理合法性检查全绿（Vdc_min≥689.9 V、
能量闭合 ≤0.004%）→ fleet_profiles。同时做 **K-shape 覆盖度审计**：v2 相对 v1
明显铺开（跨集最近邻 SBD median ~0.2），证明"v2 数据本身真的比 v1 好"——
这一步的目的不是训练 AI，而是先证明数据。

**T-303：把航次变成 NN 能训练的数据**。滑动窗口（过去 300 s 历史 → 未来 300 s
目标量，每 10 s 一个窗口，窗口不跨航次），155,087 个窗口，航次级 split
**train 280 / val 60 / test 60**（seed 固定），归一化仅在 train 拟合，泄漏断言全过。
另做 **FR-316 跨 split 近邻重复审计**：3 对形状相似的航次，逐一裁决为
kept_declared（连续随机化保证幅值与标签各异，非模板泄漏）——机制留痕，不静默。

### 7.4 阶段二：把训练框架升级为统一平台（T-304）✅

训练程序从"MLP/LSTM 专用"改造为统一平台：
`--arch {mlp,tcn,cnn_mlp,nbeats}` × `--dataset {v1,v2}` × `--quantiles`。
**回归保护**：默认参数在 v1 上复跑，val RMSE 9.268 vs 既有记录 9.303
（容差 ±0.05 内，差异来自 TF 版本数值路径）——证明扩展没有破坏老路径。
所有新架构的算子都限定在 NPU 白名单内（Conv1D/Dense/池化/ReLU/Add/Concat）。

### 7.5 阶段三：TCN 主推 + 公平对照（T-305 / T-306 / T-307）🔄

**为什么主推 TCN**：普通 MLP 把 300 s 的所有数字铺平一次看；TCN 用因果卷积按
时间结构看——局部变化（dilation=1）→ 中期（2,4,8）→ 长期（16,32），七层残差块
后感受野 R=381 ≥ 300 s，完整覆盖历史。同时主体算子是 Conv1D——**正是 NPU 最擅长
的算子**，这就是"边缘 AI"选它的理由。预测目标不变：未来 300 s 能量需求。

**过程中的一次重要排障（诚实记录）**：TCN 首训 val RMSE=16.88 kWh，与"什么都不
预测的常数中位数"（16.87）几乎相同——模型完全塌缩。通过只读诊断 + 对照实验
（同架构 MSE 能学、pinball 不能学）定位了**两个独立根因**：
① 池化层抹掉了"当前时刻在航次中的位置"信息（架构设计失误）；
② 分位数损失里一处 `(N,1)−(N,)` 广播成 (N,N) 的逐对交叉矩阵（代码 bug）。
修复后 tiny-overfit 验证：TCN 学习能力恢复到与 MLP 同水平（8.71 vs 8.64 kWh）。
教训已入开发日志：**新架构必须先过 tiny-overfit 冒烟测试，再上全量训练**。

**T-305 规模扫描**（进行中）：f16/f32/f64/f128 四个规模点在 MacBook M1（GPU 提速
10~30×）上以统一协议（100 epoch cap + patience 10 早停）执行，Windows 上的
f16 结果作跨机 sanity anchor。

**T-307：不只看准不准，还看"值不值得放到 N6"**。举一个假设的例子说明裁决逻辑：

| 模型 | 参数量 | RMSE | INT8 大小 | NPU 速度 |
|---|---|---|---|---|
| Tiny | 20k | 10.0 | 25 KB | 很快 |
| Medium | 80k | 8.8 | 90 KB | 快 |
| Large | 500k | 8.5 | 550 KB | 慢 |

Large 的 RMSE 最好（8.5<8.8），但为了 0.3 kWh 的改善模型大 6 倍——可能完全
不值得。**精度 × 闭环收益 × NPU 成本**共同选模，这是"边缘 AI"课题的核心部分。

### 7.6 阶段四：解决"AI 有时候会预测错"（T-308 / T-309 / T-310）

**分位数输出的含义**（所有模型统一升级）：网络不再只输出
ŷ=100 kWh，而是输出 q10=88、q50=101、q90=120——中位预测 101，不确定性区间
[88,120]。区间窄（90/100/110）说明网络有把握；区间宽（30/100/190）说明网络
自己都没把握。这个信号将直接用于 EMS 安全门控。

**T-308：训练工况识别器（候选，不一定部署）**。回答"现在船处于什么工况"
（eco/rush/bridge/port/逆水…），输入仍然只能是过去的历史——目的在于发现
"哪些工况下预测器特别容易犯错"。**是否值得部署由 T-310 的 G0~G3 消融裁决**：
G0 无保护 / G1 只用分位数门控 / G2 只用工况门控 / G3 两者都用。若 G1 已够好，
就不额外放一个分类网络。

**T-309：决定"AI 什么时候可以被相信"（控制设计任务）**。例如：正常时 100% 使用
NN 信息；q90−q10 区间过宽 → NN 影响减半；更危险 → NN 完全关闭、退回普通
A-ECMS（Predictive AECMS → AECMS）。**AI 错了不能强行继续控制。**

**T-310：最终回 Simulink 做闭环考试**。RMSE/MAE/R² 都只是机器学习指标；
T-310 把 NN 放回 EMS 闭环（NN 预测 → Predictive ECMS → P_gen/P_bat → ModelD →
SOC/fuel/母线/航次），检查它是否真的让船舶 EMS 更好。重点场景 S20 检验 Phase 2
已知问题是否被修好（benefit gate），另有 10+ 条完全留出的新航次确认没有
"修好 S20 搞坏别处"（non-degradation gate）。

### 7.7 阶段五：真正部署 STM32N6（T-311）

最终选出的模型走完整部署链：FP32 TensorFlow → INT8 量化 → ST Edge AI →
Neural-ART compiler → STM32N647。在**真实硬件上**验证五件事：量化前后精度差、
内存占用（weights/activation RAM/model size）、NPU 算子映射率（多少算子真正跑在
Neural-ART 上而不是掉回 Cortex-M55 CPU）、推理时延、PC 与板端输出一致性
（FR-319 板上 int8 验证）。

### 7.8 阶段六：证明一切不是碰巧跑出来的（T-312）

干净进程重跑关键实验、检查 manifest 与数据 hash、验证训练/结果可复现、
更新 README、整理最终报告、确保 Git clean——给整套 Phase 2.5 封箱。

## 9. 研究诚信与工程纪律

本研究的全过程遵循以下纪律（这些不是形式，而是从两次 NO-GO 中提炼的教训）：

### 9.1 先验证上限，再投入施工

每个 Phase 的 gate 判定都是机器可读的（JSON），不达标就不进入下一阶段。Phase 0 的 DECISION_REQUIRED → 用户裁决 GO，Phase 1 的 PROCEED_TO_PHASE2_NN，Phase 2 的 PARTIAL → 用户裁决带 C4 进 Phase 3——每一步都有明确的决策记录。

### 9.2 诚实报告失败

- 前两轮 NO-GO 完整记录（不是只报成功）

### 9.3 优化假目标红线
