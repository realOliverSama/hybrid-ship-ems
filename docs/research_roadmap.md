## 1. 研究背景与动机

### 1.1 问题场景

某型近海工作船采用**甲醇-电池混合动力**：
- 甲醇发电机组（潍柴 WH17ME 系列，500 kW/单机 ×2，直流母排）
- 动力电池（1071.36 kWh，576 V × 930 Ah/侧 ×2）
- 直流母排下机组转速与推进负荷解耦

**能量管理的核心问题**：甲醇机的燃油消耗率（BSFC）随负荷强烈非线性变化——低负荷时恶化显著（最优 427 g/kWh，25% 负荷时恶化 +30%~+70%）。电池作为能量缓冲，可以在低负荷时放电（让机组少发或不发）、高负荷时充电（让机组高效运行），从而**把机组运行点搬移到高效区**。

**研究目标**：设计一种能量管理策略（EMS），在保证电量维持（电池不放干）的前提下，最小化全程甲醇消耗。

### 1.2 为什么值得研究

这个方向不是凭空设想的——它的动机来自**两次失败的尝试**（详见 §2），以及一个关键的物理观察：BSFC 曲线的非线性意味着"运行点优化"空间真实存在。但**空间存在 ≠ 实时算法能捕获**——这正是本研究要回答的问题。

---

## 2. 研究问题的演化：两轮 NO-GO 的教训

本研究是**第三次立项**。前两次尝试均因"收益上限在机理层面不存在"而 NO-GO，且都是在控制器施工完成后才发现：

| 轮次 | 路线 | NO-GO 原因 | 教训 |
|---|---|---|---|
| 第一轮 | timed-feedforward（定时前馈） | 收益上限机理锁死 | 控制器做完才发现上限不存在 |
| 第二轮 | multistep-predictive（多步预测） | 功率时序优化被往返损耗锁死 | 同上 |

**由此确立本研究的第一纪律**（brainstorm D1）：

> **先用离线最优（DP）验证节油收益上限存在，再投入任何控制器施工。**

这条纪律贯穿整个研究：每个 Phase 的 gate 判定都是机器可读的（JSON），不达标就不进入下一阶段，避免"施工到底才发现方向错了"的沉没成本。

## 4. Phase 0：离线收益上限验证

### 4.1 要回答的问题

> 在不考虑实时可实现性的前提下，这艘船的理论节油上限是多少？

如果上限都不到 5%，任何实时策略都不值得做（文献典型 ECMS 只能捕获上限的 60~90%）。

### 4.2 实验步骤

```text
① 设备真实参数落模（电池 1071.36 kWh、充放 1050 kW、BSFC 双锚点 427/453 g/kWh）
② BSFC 曲线族构造（双真实锚点 + 三档低负荷恶化敏感性：+30%/+50%/+70%）
③ 8 个典型场景的需求负荷剖面提取（Baseline EMS 导出，因果隔离验证）
④ 离线动态规划（DP）全局最优求解（SOC 状态网格 × P_gen 控制网格，后向归纳）
⑤ 敏感性矩阵（BSFC 档位 × 最低稳定负荷 × 爬坡率 × 电池容量）
⑥ 机器可读 GO/NO-GO 判定
```

**关键设计决策**：
- **因果隔离**：P_demand(t) 从降额与 EMS 作用之前提取，用两种控制律重复提取验证不变性（逐点偏差 <0.1%），避免"用被 EMS 影响的负荷去评估 EMS"的因果污染
- **双锚点标定**：BSFC 曲线只有两点是真实的（427 最优、453 额定），其余形状为假定——用三档敏感性量化这个不确定性
- **终端电量维持对称带**：|SOC(T)−SOC(0)| ≤ 0.005，防止 DP"借电"制造虚假节油

### 4.3 结果

| 口径 | 8 场景节油上限 | 判定 |
|---|---|---|
| 连续运行（主判定，P_min=400 kW） | 0.50% ~ 4.22% | 无场景 ≥5% |
| 同可行域（P_min=0） | 3.64% ~ 4.61% | — |
| 电池容量敏感性 | 643→0.93%，1500→6.09% | 强杠杆 |

**机器判定：DECISION_REQUIRED（tier=NONE）**——不到 5% 的 GO_ROBUST 线，也不到全低于 2% 的 NO-GO 线，落灰区。

**用户裁决：GO_TO_PHASE1**——收益机理真实存在（运行点优化，与前两轮"时序优化被锁死"机理不同），且电池容量是强杠杆（若实船电池可超配则上限可过 5%）。

### 4.4 本阶段的核心贡献

- 建立了**可复现的离线上限验证工具链**（DP 求解器 + 因果隔离 + 敏感性矩阵）
- 证明了收益机理的真实性（BSFC 非线性运行点搬移）
- 提供了 Phase 1 的标杆（DP 值将作为"上限"衡量实时算法的捕获率）

## 5. Phase 1：实时 ECMS 控制器链

### 5.1 要回答的问题

> 不依赖未来信息的实时 ECMS，能捕获 DP 上限的多少？加上"完美的未来信息"（oracle）又能再补多少？

### 5.2 控制器家族（递进设计）

| 控制器 | EMS_CTRL_LAW | 策略 | 依赖信息 |
|---|---|---|---|
| C0 | 0 | Baseline 规则（负荷跟随） | 当前负荷 |
| C1 | 4 | Fixed ECMS（λ 固定） | 当前 SOC + 负荷 |
| C2 | 5 | SOC-Adaptive ECMS（λ 随 SOC 偏差自适应） | 当前 SOC + 负荷 |
| C3 | 6 | Oracle Predictive A-ECMS（C2 + 真实未来剖面前瞻） | 当前 + **全知未来** |
| DP | — | 离线全局最优 | 全知未来 |

**ECMS 核心思想**：每步在 P_gen 可行网格上求 `argmin [ṁ_f(P_g) + λ·P_bat_eq]`——把电池的充放电折合成"等效燃油"，λ 是电价因子（kg/kWh）。

**三个研究问题**：
- **RQ1**：实时 ECMS（C2）捕获 DP 上限的比例是多少？
- **RQ2**：SOC 自适应（C2 vs C1）的增量价值是什么？
- **RQ3**：Oracle 前瞻（C3 vs C2）的增量是多少？——这是 Phase 2 NN 立项的量化依据

### 5.3 关键实验：复合航次 S20

为什么需要复合航次？Phase 0 的 8 个场景都是单一工况（静水/顺水/逆水等），15 分钟航程太短，SOC 自适应的价值体现不出来。S20 是 11 航段、92 分钟、22.5 km 的复合航次（离泊→港区限速→经济巡航→赶班→桥区限速→逆水→靠泊），低负荷段占 56.1%——足够长、足够多变，才能让 SOC 轨迹的"漂移 vs 紧致"差异显现。

### 5.4 结果（S20 复合航次，tier2 BSFC）

| 控制器 | fuel_corr [kg] | saving vs C0 | SOC_end | 捕获 DP 上限 |
|---|---|---|---|---|
| C0 Baseline | 349.00 | — | 0.5784 | — |
| C1 Fixed ECMS | 324.92 | +6.90% | **0.4394（出带）** | 72.6%* |
| C2 SOC-Adaptive | 330.66 | +5.26% | 0.6002 ✓ | **55.3%** |
| C3 Oracle Predictive | 324.96 | +6.89% | 0.6039 ✓ | **72.5%** |
| DP | 315.83 | +9.51% | 0.5963 ✓ | 100% |

*C1 出带（SOC 放到 0.44），其数字依赖大偏移下的线性修正，仅供参考。

**三个 RQ 的答案**：
- **RQ1**：C2 捕获 **55.3%**（实时、电量维持合规）
- **RQ2**：SOC 自适应的价值不是单场景节油，而是**跨航程的电量维持可迁移性**——C1 的 S01 标定 λ 在 S20 上失控（SOC 漂到 0.44），C2 全程紧致 [0.596, 0.602]
- **RQ3**：oracle 增量 **+1.63 pp**（S20 入带口径）≥ 0.5 pp 阈值

**机器判定：PROCEED_TO_PHASE2_NN**——完美未来信息有真实经济性价值（+1.63 pp），值得用 NN 去逼近。

### 5.5 本阶段的核心贡献

- 建立了完整的**实时 ECMS 控制器家族**（C1/C2/C3）+ 消融实验设计
- 证明了 SOC 自适应的必要性（跨航程电量维持）
- 量化了预测的价值（+1.63 pp），为 Phase 2 提供了立项依据
- 所有控制器为嵌入式可行设计（单步网格穷举 ≤200 点，无迭代优化器）

## 6. Phase 2：NN 预测通道

### 6.1 要回答的问题

> 用神经网络实时预测未来负荷，替代 Phase 1 中的 oracle（全知未来），能捕获多少预测增量？

- **RQ4**：NN 预测捕获 oracle 增量的比例（capture rate）
- **RQ5**：对未见过的新航次泛化如何
- **RQ6**：部署预算能否落进 STM32N6

### 6.2 预测目标设计

**关键决策**：预测**未来 300 s 能量需求 Ê_H(t) = Σ P_demand(t+1..t+300)/3600 [kWh]**，而非瞬时峰值。

为什么？前两轮 NO-GO 的教训：瞬时峰值预测是"时序优化"思路，被往返损耗锁死。能量需求预测是"运行点优化"思路，与 BSFC 非线性的节油机理对齐。

**控制器接入**：Ê_H 经 SOC_ref 前瞻通道驱动（`SOC_ref_eff = SOC_ref + K_S·ê`，K_S=0.01 保守增益）——与 Phase 1 的 C3 oracle 通道同构，构成 law=7（C4 NN-A-ECMS）。

### 6.3 数据与模型

- **fleet-200**：随机航次生成器（7 类积木）生成 200 条多样化航次，S20/S01/S02/S07 结构性隔离（不进任何 split）
- **数据集**：77,586 窗口，输入 302 维（P_demand 300 s 历史 + v_ship + accel），航次级 split **140/30/30**，归一化 fit-on-train
- **选模**：MLP 302-128-64-1（47,105 参数）击败 LSTM 对照（val RMSE 9.30 vs 10.68）
- **泄漏检查**：窗口不跨航次、split 互斥、首尾裁剪——全过

### 6.4 Simulink 集成：内联失败 → extrinsic 兜底

**原方案**：MLP 前向内联进 MATLAB Function 块（Stateflow EML）。遭遇 `Stateflow:cdr:ErrorsParsingEmlFcn` 解析失败——系统性攻坚排除了代码语法、图对象、接线、参数值、转置形式、尺寸声明（证据链存档），根因为 **R2026a EMChart 跨块变量数据流缺陷**（已备 MathWorks 提交材料）。

**兜底方案**（Amendment v1.2）：NN 前向改 `coder.extrinsic` 调用 MATLAB 函数。科学上零损失（消融语义不变），且 extrinsic 边界恰好对应 Phase 3 的 NPU 推理 / MCU 控制分工。

**验证链**：build law 0~7 全编译；T1 函数 vs Python max|Δ|=1.2e-14；T2 回退逐位 ≡ law=6(ê=0)；T3 S01 闭环 fuel=91.23 kg（与 golden 逐位一致）。

### 6.5 结果（S20 复合航次）

| 控制器 | fuel_corr [kg] | saving vs C0 | 备注 |
|---|---|---|---|
| C0 Baseline | 349.002 | — | Phase 1 复用 |
| C2 A-ECMS（规则） | 330.662 | 5.26% | Phase 1 复用 |
| **C4 NN-A-ECMS** | **328.549** | **5.86%** | 本阶段新跑 |
| C3 oracle-A-ECMS | 324.957 | 6.89% | 上界参照 |
| DP | 315.83 | 9.51% | 物理上界 |

**nn_oracle_capture = (330.662−328.549)/(330.662−324.957) = 0.3704 → PARTIAL**

- C4 捕获 oracle 增量的 **37%**，未达 ≥50% 合格线
- 留出泛化 **median = −0.232%**（4/10 航次为正）——收益依赖航次结构，不是普遍增益
- 部署预算**完全满足**（47k 参数、184 KB、<1 ms 推理）

### 6.6 失败模式与诚实结论

- **S07 桥区机动恶化 1.2 kg**：长时低功率段 + 突发操纵，NN 按平均能量预测导致 SOC_ref 偏移方向错误——Phase 3 需门控保护
- **低估偏向**（under_freq=0.426）：预测偏保守 → 放电偏多，在 S20 恰好有利、在 S07 有害——收益方向依赖航次结构
- **预测精度天花板**：R²≈0.73，约 27% 的未来能量方差不可由历史 300 s 解释（浪、流随机分量）——这是纯历史外推的理论上限

**机器判定：PARTIAL**。**用户裁决：带 C4 进 Phase 3**（C2 为主控制器、C4 为边缘实验对照），理由：
- C4 从未显著劣化 S20，且部署成本极小
- S07 门控保护纳入 Phase 3 设计
- 论文结论成立且诚实："预测通道的价值取决于航次可预测性"

### 6.7 本阶段的核心贡献

- 完成了**从 oracle 到 NN 的完整替代验证**（消融实验设计：C0/C2/C4/C3/DP 五级对照）
- 诚实报告了边界结果（37% capture、泛化中性）——不夸大、不隐藏失败
- 建立了**可复现的数据集/训练/集成/验证工具链**（fleet 生成器 + 泄漏检查 + 双平台交叉验证）

## 7. Phase 3（规划）：STM32N6 边缘部署

### 7.1 要回答的问题

> 这套 EMS（C2 主 + C4 对照）能不能部署到真实硬件上？边缘 AI 的实际价值是什么？

### 7.2 技术路线

**硬件平台**：AlienTek STM32N647（ARM Cortex-M55 + NPU）

**分工架构**（与仿真同构）：
- **NPU**：NN 推理（TFLite，47k 参数，<0.01 ms 量级）
- **MCU**：控制逻辑（law=6 内核，单步网格穷举）

**关键设计**：
- S07 类失败模式的**门控保护**（场景分类 → 切换 C2 或加下限）
- HIL（Hardware-in-the-Loop）验证
- N6 算力评估笔记：当前 MLP 仅 47k 参数/1 Hz，M55 微秒级即可胜任，NPU 算力大量闲置——Phase 3 可研发更复杂预测模型（LSTM/多步概率）兑现边缘 AI 算力价值，全软件路线作为保底

### 7.3 预期产出

- C2/C4 在 STM32N6 上的实时运行证据
- HIL 闭环验证（仿真 vs 硬件一致性）
- S07 门控保护的有效性验证
- 边缘 AI 算力利用率分析

## 8. 研究诚信与工程纪律

本研究的全过程遵循以下纪律（这些不是形式，而是从两次 NO-GO 中提炼的教训）：

### 8.1 先验证上限，再投入施工

每个 Phase 的 gate 判定都是机器可读的（JSON），不达标就不进入下一阶段。Phase 0 的 DECISION_REQUIRED → 用户裁决 GO，Phase 1 的 PROCEED_TO_PHASE2_NN，Phase 2 的 PARTIAL → 用户裁决带 C4 进 Phase 3——每一步都有明确的决策记录。

### 8.2 诚实报告失败

- 前两轮 NO-GO 完整记录（不是只报成功）
- Phase 2 的 PARTIAL（37%）如实呈现，包含失败模式分析（S07 恶化、低估偏向）
- 留出泛化 median −0.23% 如实报告（"平均不优于 C2"）
- law=7 内联失败的完整证据链存档（MathWorks bug 材料已备）

### 8.3 优化假目标红线

不及预期的指标不在缺省/估计参数上硬调（BSFC 低负荷形状、最低稳定负荷等仍为假设值）。所有候选优化方向列入 backlog（`docs/optimization_backlog.md`），待真实参数到位后按优先级重启。

### 8.4 可复现性

- 全部流程脚本驱动（禁止 GUI 手工状态）
- 大型 .mat 不入库，runs.csv/JSON/报告入库
- 复现脚本（55_repro_check.sh）验证逐位一致
- 双平台交叉验证（Windows 训练 + Mac 验证）
